## SECTION 1: SYSTEM OVERVIEW

### 1.1 What is Attendrix

Attendrix is a distributed, intelligent, paperless attendance management system designed specifically for the operational realities of universities in Buea, Cameroon. It is a production-grade web application that replaces manual, paper-based attendance tracking with a secure, real-time, multi-tenant digital platform. The system handles the entire attendance lifecycle—from session creation by lecturers, through student check-in using QR codes and face verification, to real-time analytics, reporting, and multi-campus data synchronization.

### 1.2 Purpose of the System

The purpose of Attendrix is to solve the chronic problem of attendance fraud (proxy attendance), manual record-keeping errors, and lack of real-time visibility into student participation across university campuses. Universities in Buea face specific challenges: intermittent internet connectivity, power fluctuations, multiple geographically separated campuses (campus nodes), and a need for both centralized cloud oversight and local offline resilience. Attendrix was engineered to operate correctly under these conditions.

### 1.3 Problem It Solves

The fundamental problems Attendrix addresses are:

1. **Proxy Attendance:** Students asking classmates to mark attendance on their behalf. Attendrix defeats this through QR-code session validation, device fingerprinting, IP tracking, geolocation verification, and face verification using client-side face-api.js matched against server-enrolled 128-dimension face descriptors.

2. **Manual Error and Fraud:** Paper registers are lost, altered, or inaccurately filled. Attendrix provides cryptographically verified, audit-logged digital attendance records.

3. **Lack of Real-Time Visibility:** Administrators and lecturers cannot know attendance patterns until registers are manually compiled. Attendrix provides real-time dashboards with live event streaming via Server-Sent Events (SSE) and MQTT messaging.

4. **Multi-Campus Fragmentation:** Each campus operates independently with intermittent connectivity to a central cloud. Attendrix implements an offline-first queue-based synchronization engine with exponential backoff retry, conflict resolution, and store-and-forward messaging.

5. **Data Silos:** Attendance data is isolated per institution. Attendrix implements multi-tenant isolation at the application layer and at the database security rules layer, ensuring institutional data separation.

### 1.4 Institutions and Users Involved

The system is designed for:

- **Super Administrators:** Manage the entire Attendrix platform across all institutions. Have system-wide visibility and configuration access.
- **Institutional Administrators:** Manage a single university or institution. Create departments, manage users, configure attendance policies, and view institution-wide analytics.
- **Lecturers:** Create attendance sessions for their courses, generate session codes/QR codes, monitor live attendance marking, and close sessions. They are the primary operators of the system during lectures.
- **Students:** Enroll their faces, scan QR codes generated by lecturers, have their faces verified against enrolled descriptors, and mark their attendance. They can view their own attendance history and analytics.
- **Employees:** A role for non-academic staff attendance tracking, with leave request functionality.

### 1.5 Objectives of the System

1. Provide a secure, anti-proxy attendance tracking mechanism combining QR codes and face verification.
2. Enable real-time attendance monitoring and analytics through live dashboards and event streaming.
3. Ensure reliable operation during network outages through offline-first queue synchronization.
4. Support multi-campus, multi-institution deployment with full data isolation.
5. Provide comprehensive security controls including RBAC, MFA, WebAuthn, device fingerprinting, and geolocation enforcement.
6. Generate automated reports (PDF, XLSX, CSV) for academic record-keeping.
7. Enable predictive analytics for at-risk student identification using machine learning (scikit-learn).
8. Provide a smart campus intelligence suite for infrastructure monitoring, classroom participation analysis, and automated intervention.

### 1.6 Real-World Operational Context

The system is deployed in a context where:

- **Internet connectivity is unreliable.** Power outages and ISP downtime are frequent. The system must work offline and sync when connectivity returns.
- **Multiple campuses exist within a single institution.** Each campus may have its own local network, MQTT broker, and database node. These nodes must synchronize with each other and with a central cloud instance.
- **Bandwidth is constrained.** Synchronization must be bandwidth-aware, batching operations and prioritizing critical data.
- **Academic semesters have fixed schedules.** The system must support recurring schedules, session creation aligned with academic timetables, and conflict detection for room and lecturer allocation.
- **Students may attempt to bypass attendance controls.** The system must employ defense-in-depth security: QR codes that expire, session codes validated server-side, device fingerprints, geolocation fences, and face verification—all enforced simultaneously.
- **Regulatory compliance is required.** Attendance records are legal academic documents. The system must provide immutable audit logs, tamper-evident records, and exportable reports for academic boards.

## SECTION 2: FULL TERMINOLOGY DOCUMENTATION

### 2.1 Core Technologies and Protocols

#### MQTT (Message Queuing Telemetry Transport)

- **Full Meaning:** MQ Telemetry Transport
- **Explanation:** A lightweight publish-subscribe network protocol designed for constrained networks. It uses a broker to route messages between publishers and subscribers on specific topics.
- **Purpose in Attendrix:** Used for real-time attendance event dissemination. When a student marks attendance, the system publishes a message to `attendrix/attendance/{session_id}` which any subscribed component (dashboards, analytics engines, other campus nodes) receives instantly.
- **Why Selected:** MQTT is chosen over HTTP polling because it provides immediate event delivery with minimal bandwidth overhead. It supports Quality of Service (QoS) levels for guaranteed delivery, has built-in last-will-and-testament for node failure detection, and operates efficiently over unreliable networks—critical for the Cameroonian university context.
- **How It Works:** The `MqttService` class (in `src/infrastructure/mqtt_service.py`) wraps the paho-mqtt library. On initialization, it either connects to a real Mosquitto broker (in production) or operates in mock mode (in development). Topics are structured hierarchically: `attendrix/attendance/{session_id}`, `attendrix/session/{session_id}`, `attendrix/network/{device_id}`, `attendrix/notifications/{user_id}`, `attendrix/system/health`. The service implements automatic reconnection, topic wildcard matching (`+` and `#`), and handler registration. Published messages include the student_id, status, timestamp, and source identifier. The docker-compose.yml runs an `eclipse-mosquitto:2` container as the broker.

#### VPN (Virtual Private Network)

- **Full Meaning:** Virtual Private Network
- **Explanation:** A technology that creates an encrypted tunnel between two or more network endpoints over a public network, allowing them to communicate as if on the same local network.
- **Purpose in Attendrix:** Used conceptually in the distributed architecture where multiple campus nodes (e.g., Science Block, Engineering Block, HTTTC Annex) communicate securely. The system is designed to operate over a VPN infrastructure connecting these campus networks, enabling encrypted node-to-node communication for database synchronization.
- **Why Selected:** VPN technology provides the encrypted backbone for multi-campus communication without exposing internal APIs to the public internet. This is essential for the distributed node architecture where campus-level MQTT brokers and database instances must synchronize securely.
- **How It Works:** The infrastructure topology in the system shows nodes like "Science Block," "Engineering Block," and "Central Library" communicating with the central attendrix-web instance. While VPN tunneling is handled at the infrastructure level (not in application code), the system's network nodes and peer-to-peer sync status API endpoints (`/api/institutional/p2p-sync`, `/api/institutional/network-status`) provide visibility into this VPN-based mesh network.

#### JWT (JSON Web Token)

- **Full Meaning:** JSON Web Token
- **Explanation:** A compact, URL-safe token format defined by RFC 7519 for representing claims securely between two parties. Tokens are digitally signed using HMAC with SHA-256 (HS256).
- **Purpose in Attendrix:** JWT is the authentication backbone. Every API request after login must include a Bearer token in the Authorization header. The token carries the user_id, email, role, institution_id, and a unique jti (JWT ID) for replay protection. Access tokens expire in 1 hour; refresh tokens expire in 30 days.
- **Why Selected:** JWTs are stateless—the server does not need to maintain session state, which is critical for a distributed system where any node may handle a request. They are compact, can be verified without database lookups (beyond checking revocation), and support custom claims for role-based authorization.
- **How It Works:** `AuthenticationService._generate_access_token()` creates a JWT with claims including `user_id`, `jti`, `email`, `role`, `institution_id`, `exp`, `iat`, and `type`. The token is signed with `JWT_SECRET_KEY` (minimum 64 chars, validated on startup). The `require_auth` decorator extracts the token from the Authorization header, verifies it via `AuthenticationService.verify_token()`, checks the Redis token blacklist for revocation, and loads the token payload into `request.current_user`. `require_role` then validates the user's role against allowed roles. JWT rotation is handled by `JWTRotationManager` (in `api_security.py`).

#### API (Application Programming Interface)

- **Full Meaning:** Application Programming Interface
- **Explanation:** A set of defined rules and protocols for software components to communicate with each other.
- **Purpose in Attendrix:** The system exposes a comprehensive RESTful JSON API at `/api/` endpoints covering authentication, attendance, biometrics, scheduling, user management, analytics, reporting, security monitoring, offline queue management, and infrastructure monitoring.
- **Why Selected:** RESTful APIs provide platform independence—the Python/Flask backend can serve any frontend (web, mobile, desktop). JSON encoding is lightweight and universally parsable.
- **How It Works:** Flask route decorators (`@app.route('/api/...')`) map HTTP methods and paths to Python handler functions. Request validation uses marshmallow schemas and custom validators. Responses are JSON-serialized dictionaries. Authentication is enforced via the `@require_auth` and `@require_role` decorator chain. Rate limiting is applied at both the NGINX reverse proxy level and application level.

#### REST (Representational State Transfer)

- **Full Meaning:** Representational State Transfer
- **Explanation:** An architectural style for designing networked applications that uses stateless operations and standard HTTP methods (GET, POST, PUT, DELETE) on named resources.
- **Purpose in Attendrix:** All API endpoints follow REST conventions. Resources like users (`/api/users/profile`), attendance sessions (`/api/attendance/create-session`), schedules (`/api/schedules`), and institutions (`/api/institutions`) are manipulated through standard HTTP verbs.
- **Why Selected:** REST is the industry standard for web APIs. It provides predictable URL structures, leverages HTTP status codes for error reporting, and is cacheable, which is important for bandwidth-constrained environments.
- **How It Works:** The system uses Flask route definitions that map to CRUD operations. For example, `GET /api/users/profile` reads the current user; `PUT /api/users/profile` updates it. Error responses use appropriate HTTP status codes: 400 for validation errors, 401 for authentication failures, 403 for authorization failures, 404 for missing resources, 429 for rate limiting, and 500 for server errors.

### 2.2 Networking and Infrastructure

#### LAN (Local Area Network)

- **Full Meaning:** Local Area Network
- **Explanation:** A network that connects computers within a limited geographic area, such as a university campus.
- **Purpose in Attendrix:** Each campus node operates on its own LAN. The system is designed for intra-campus LAN communication where MQTT brokers, local database instances, and web application nodes communicate with low latency. When a student scans a QR code in a lecture hall, the attendance marking request flows within the campus LAN to the local web node.
- **Why Selected:** LAN communication ensures that core attendance operations (QR scanning, face verification, attendance marking) function even when the internet connection to the central cloud is down. This is essential for the offline-first architecture.
- **How It Works:** The docker-compose.yml defines `attendrix-network` with subnet `172.20.0.0/16` using bridge driver, enabling container-to-container communication within the same Docker host or across Docker swarm nodes connected via LAN.

#### WAN (Wide Area Network)

- **Full Meaning:** Wide Area Network
- **Explanation:** A telecommunications network that extends over a large geographic area, connecting multiple LANs.
- **Purpose in Attendrix:** WAN connectivity links the central cloud deployment (at attendrix.app) with campus-level nodes. Multi-campus synchronization, cloud backup, and centralized admin dashboards all operate over WAN.
- **Why Selected:** Universities in Buea have campuses spread across different neighborhoods. WAN connectivity is required for centralized management of these distributed campus nodes.
- **How It Works:** The NGINX reverse proxy handles WAN-facing HTTPS traffic. Cloudflare provides CDN, DDoS protection, and WAF between the public internet and the attendrix-web application servers.

#### RFID (Radio-Frequency Identification)

- **Full Meaning:** Radio-Frequency Identification
- **Explanation:** A technology that uses electromagnetic fields to automatically identify and track tags attached to objects.
- **Purpose in Attendrix:** Not directly implemented in the current codebase. The system's architecture supports future integration with RFID readers for physical card-based attendance marking as an alternative to QR codes. The anti-proxy attendance security module currently focuses on QR + face verification.

#### IoT (Internet of Things)

- **Full Meaning:** Internet of Things
- **Explanation:** A network of physical devices embedded with sensors and connectivity that enables them to collect and exchange data.
- **Purpose in Attendrix:** The Smart Campus Intelligence Suite (innovation modules) conceptualizes IoT integration for infrastructure monitoring—UPS status, generator status, ISP connectivity, and network node health. The system provides API endpoints for upserting UPS, ISP, and generator status data.
- **Why Selected:** IoT integration enables automated infrastructure monitoring, reducing manual checks and providing real-time visibility into campus operational health.
- **How It Works:** Endpoints like `/api/institutional/infrastructure/ups` and `/api/institutional/infrastructure/isp` accept POST requests with sensor data. The dashboard displays this infrastructure data alongside attendance analytics.

### 2.4 Security Technologies

#### HTTPS (Hypertext Transfer Protocol Secure)

- **Full Meaning:** Hypertext Transfer Protocol Secure
- **Explanation:** HTTP over TLS/SSL encryption, ensuring that all data exchanged between client and server is encrypted.
- **Purpose in Attendrix:** All production traffic between browsers and the Attendrix API is encrypted via HTTPS. The NGINX reverse proxy terminates TLS connections and proxies to the Flask backend.
- **Why Selected:** HTTPS prevents man-in-the-middle attacks, eavesdropping, and tampering with attendance data in transit. This is mandatory for a system handling authentication tokens, biometric descriptors, and academic records.
- **How It Works:** The NGINX configuration (`nginx.conf`) listens on port 443 with SSL certificates (`ssl_certificate` and `ssl_certificate_key`). It enforces TLSv1.2 and TLSv1.3 only, with strong cipher suites (ECDHE-ECDSA-AES128-GCM-SHA256 etc.). HTTP on port 80 redirects to HTTPS (301 redirect). HSTS headers enforce HTTPS at the browser level for 1 year.

#### TLS (Transport Layer Security)

- **Full Meaning:** Transport Layer Security
- **Explanation:** A cryptographic protocol providing secure communication over a computer network. TLS 1.2 and 1.3 are the current standards.
- **Purpose in Attendrix:** Underlies all HTTPS connections. Also used for SMTP STARTTLS for email delivery, and for securing Redis connections in transit.
- **Why Selected:** TLS is the industry standard for transport encryption. It provides confidentiality (encryption), integrity (HMAC), and authentication (certificate-based).
- **How It Works:** The NGINX configuration specifies `ssl_protocols TLSv1.2 TLSv1.3;` with `ssl_prefer_server_ciphers on;`. SSL session caching is enabled (`ssl_session_cache shared:SSL:50m;`). OCSP stapling is configured for certificate status checking.

#### RBAC (Role-Based Access Control)

- **Full Meaning:** Role-Based Access Control
- **Explanation:** An approach to restricting system access to authorized users based on their organizational role. Permissions are assigned to roles, and users are assigned to roles.
- **Purpose in Attendrix:** The entire authorization architecture is RBAC. Five roles exist: `super_admin`, `institutional_admin`, `lecturer`, `student`, `employee`. Each role has a predefined set of permissions defined in `RolePermissions.PERMISSIONS`.
- **Why Selected:** RBAC is the most practical access control model for an educational institution where users naturally fall into well-defined roles. It simplifies permission management—administrators assign roles, not individual permissions.
- **How It Works:** The `require_role(*allowed_roles)` decorator checks `request.current_user.get('role')` against allowed roles. Additionally, `require_permission(*permissions)` checks granular permissions from `RolePermissions`. The `Permission` class defines constants like `MANAGE_USERS`, `MARK_ATTENDANCE`, etc. The firestore.rules also enforce role-based access at the database level.

#### Authentication

- **Full Meaning:** The process of verifying the identity of a user, device, or system.
- **Explanation:** Authentication confirms that users are who they claim to be before granting access.
- **Purpose in Attendrix:** All API access requires authentication. The system implements email/password authentication with bcrypt password hashing, JWT token-based session management, and optional WebAuthn/FIDO2 passwordless authentication for admin accounts.
- **Why Selected:** Multi-factor authentication (password + WebAuthn passkey) provides defense-in-depth. Bcrypt provides adaptive hash functions that resist brute-force attacks. JWT enables stateless authentication suitable for distributed nodes.
- **How It Works:** The login endpoint (`POST /api/auth/login`) validates email/password against the stored bcrypt hash. On success, it generates access and refresh JWTs. The `require_auth` decorator verifies the JWT on every protected request. Admin users may also need WebAuthn passkey verification (`require_admin_webauthn` decorator).

#### Authorization

- **Full Meaning:** The process of determining what an authenticated user is allowed to do.
- **Explanation:** Authorization happens after authentication and checks whether the user has permission to perform the requested action.
- **Purpose in Attendrix:** Enforced at multiple layers: route-level role checks, permission-level checks, institution-level data isolation, and document-level ownership checks.
- **Why Selected:** Defense-in-depth requires authorization checks at every layer. Even if a user authenticates, they must be authorized for every specific action.
- **How It Works:** The decorator chain `@require_auth → @require_role → @log_access` enforces authentication then authorization then auditing. The firebase_service enforces multi-tenant isolation on every database operation. The comprehensive security module (`comprehensive_security.py`) adds additional enforcement via `ResourceOwnershipValidator`, `MultiTenantIsolator`, and `AuthorizationEnforcer`.

### 2.5 Distributed Systems and Synchronization

#### Distributed Synchronization

- **Full Meaning:** The coordination of data and state across multiple independent nodes in a distributed system.
- **Explanation:** Ensuring that all nodes in the system eventually have the same data, despite network partitions, concurrent updates, and node failures.
- **Purpose in Attendrix:** Multi-campus deployment means attendance data may be created on one campus node and must propagate to other nodes and the central cloud. The offline queue service is the synchronization engine.
- **Why Selected:** Universities in Buea have campuses that may be kilometers apart with unreliable inter-campus connectivity. A synchronization engine is required to maintain data consistency across nodes.
- **How It Works:** The `OfflineQueueService` enqueues operations as documents in the Firestore `offline_queue` collection. Each operation has type, payload, status, retry count, and checksum. A sync engine processes pending operations with handler functions that dispatch to the appropriate service. Exponential backoff with jitter handles transient failures. Conflict resolution uses last-writer-wins (LWW) by default.

#### Offline-First Architecture

- **Full Meaning:** An architectural approach where the application is designed to function without a network connection, with synchronization occurring when connectivity is available.
- **Explanation:** The system queues all operations locally when offline and syncs them in FIFO order when connectivity is restored.
- **Purpose in Attendrix:** Given the unreliable internet in Buea, the system must allow lecturers to create sessions and students to mark attendance even when the internet is down.
- **Why Selected:** Offline-first is not optional—it is a requirement for the target deployment environment. Without it, the system would be unusable during the frequent internet outages experienced in Cameroonian universities.
- **How It Works:** The `OfflineQueueService` exposes endpoints for enqueuing, processing, retrying, and clearing operations. The `/api/institutional/offline-sync` endpoint accepts sync requests from campus nodes. Queue statistics show pending, synced, failed, and conflicting operations. Bandwidth estimation helps plan sync timing.

#### Face Verification

- **Full Meaning:** The process of confirming a person's identity by comparing a live capture of their face against an enrolled facial template.
- **Explanation:** Students enroll a face descriptor (128-dimension vector from face-api.js) which is stored in Firestore. During attendance marking, the client sends a face descriptor which is compared against enrolled descriptors using Euclidean distance.
- **Purpose in Attendrix:** Face verification is the primary anti-proxy mechanism. It ensures that the person marking attendance is physically present and matches their enrolled identity.
- **Why Selected:** Face verification using client-side face-api.js provides strong identity verification without needing specialized hardware. The 128-dimension descriptor approach is computationally efficient and privacy-preserving (raw images are never stored).
- **How It Works:** The `BiometricService` class handles face enrollment (`enroll_face`), verification (`verify_face`), and multi-user matching (`verify_face_against_all`). The client uses face-api.js to detect a face and compute a 128-dimension descriptor. This descriptor is sent to `/api/biometric/face/verify` which computes Euclidean distance against enrolled descriptors. A distance <= 0.45 (configurable threshold) is considered a match.

#### Anti-Proxy Attendance

- **Full Meaning:** Mechanisms designed to prevent one person from fraudulently marking attendance on behalf of another.
- **Explanation:** Multiple security layers work together to prevent proxy attendance: QR session codes (validated server-side), device fingerprinting, IP tracking, geolocation validation, and face verification.
- **Purpose in Attendrix:** Proxy attendance is the single biggest problem in university attendance systems. The anti-proxy mechanisms are the core value proposition of the system.
- **Why Selected:** Without strong anti-proxy measures, any digital attendance system is no better than paper registers. The multi-layered approach makes proxy attendance infeasible.
- **How It Works:** The `AttendanceEngine._perform_security_checks()` method runs six security checks: IP restriction, geolocation distance calculation, device fingerprint matching, rapid succession detection (same student marking multiple times in 5 minutes), multiple device detection (same student from different IPs), and time anomaly detection. Suspicious activities are logged to security_logs with risk scores.

#### Cloud Synchronization

- **Full Meaning:** The process of synchronizing data between a local node and a cloud-based central server.
- **Explanation:** Campus-level data is synced to the central Firebase/Firestore cloud instance, making it available globally for reporting and administration.
- **Purpose in Attendrix:** Cloud synchronization enables centralized monitoring, cross-campus analytics, and backup. The cloud instance at attendrix.app is the system of record.
- **Why Selected:** Cloud synchronization provides disaster recovery, enables remote administration, and powers the real-time analytics dashboards.
- **How It Works:** Firestore provides native real-time synchronization. The offline queue service provides batched sync for operations created during offline periods. The `/api/institutional/offline-queue/process` endpoint dispatches queued operations to the appropriate Firebase collections.

### 2.6 Development and Deployment

#### Docker

- **Full Meaning:** Docker (containerization platform)
- **Explanation:** A platform for developing, shipping, and running applications in containers—lightweight, portable, self-sufficient environments.
- **Purpose in Attendrix:** The entire system is containerized. The Dockerfile uses multi-stage builds (builder → production) to minimize image size. docker-compose.yml orchestrates 7 services: postgres, mosquitto, redis, web, celery-worker, celery-beat, nginx, and flower.
- **Why Selected:** Docker ensures consistent environments across development, staging, and production. It eliminates "it works on my machine" problems and simplifies deployment.
- **How It Works:** The Dockerfile builds from `python:3.11-slim`, installs dependencies in a virtual environment during the builder stage, then copies only the venv and application code to the production stage. A non-root user (`attendrix`) runs the application. Gunicorn with 4 workers serves the Flask app on port 8000.

#### NGINX

- **Full Meaning:** NGINX (engine-x)
- **Explanation:** A high-performance web server, reverse proxy, load balancer, and HTTP cache.
- **Purpose in Attendrix:** NGINX acts as the reverse proxy sitting in front of the Flask web application. It terminates TLS, enforces rate limiting, serves static files, and applies security headers.
- **Why Selected:** NGINX is proven to handle high concurrency with low resource usage. It provides enterprise-grade security features (rate limiting, access control, SSL termination) that offload work from the Python application.
- **How It Works:** The `nginx.conf` defines rate limiting zones for login, register, API, admin, attendance, voucher, OTP, upload, search, and static files. It configures real IP headers from Cloudflare, security headers (HSTS, CSP, X-Frame-Options, etc.), and proxies requests to `http://web:8000`.

#### Celery

- **Full Meaning:** Celery (Distributed Task Queue)
- **Explanation:** An asynchronous task queue/job queue based on distributed message passing. It is focused on real-time operation but supports scheduling as well.
- **Purpose in Attendrix:** Celery handles background tasks: sending SMS messages, publishing MQTT attendance events, sending demo confirmation emails, and processing the mail queue. Celery Beat schedules periodic tasks like `process_mail_queue` every 15 seconds.
- **Why Selected:** Attendance marking must be fast and responsive. Sending SMS notifications or emails synchronously would block the HTTP response. Celery offloads these slow operations to background workers.
- **How It Works:** Celery is configured in `app.py` with Redis as both broker and result backend. Tasks are defined with `@celery.task` decorator, with retry configuration (`max_retries=3`, `default_retry_delay=60`). The docker-compose.yml runs celery-worker (concurrency=4) and celery-beat containers. Flower provides web-based monitoring on port 5555.

## SECTION 3: SYSTEM ARCHITECTURE DOCUMENTATION

### 3.1 Overall Architecture

Attendrix follows a **Clean Architecture** pattern with four distinct layers:

**Presentation Layer** (`src/presentation/`): Contains HTML templates (Jinja2), static assets (CSS, JavaScript, images), route definitions (Flask blueprints), and API endpoint handlers. This layer handles HTTP request/response and template rendering only—it contains no business logic.

**Application Layer** (`src/application/`): Contains all business logic services: authentication, attendance processing, biometric verification, scheduling, dashboard data aggregation, offline queue management, report generation, payment processing, SMS delivery, and demo booking. This layer orchestrates domain entities and infrastructure services.

**Domain Layer** (`src/domain/`): Contains core business entities (User, Institution, Course, AttendanceSession, AttendanceRecord, Schedule, Voucher, etc. as dataclasses and enums) with no dependencies on external frameworks. This is the purest layer.

**Infrastructure Layer** (`src/infrastructure/`): Contains all external integrations: Firebase Firestore, MQTT broker (paho-mqtt), SQLAlchemy/PostgreSQL, Redis, email (SMTP/Resend), SMS, device fingerprinting, and all security modules (23 security modules). This layer implements the interfaces defined by the application layer.

### 3.2 Frontend Architecture

The frontend is **server-side rendered** using **Jinja2 templates**. The template structure is organized by role:

- `templates/admin/` - Admin dashboard views
- `templates/student/` - Student dashboard views
- `templates/lecturer/` - Lecturer dashboard views
- `templates/super-admin/` - Super admin management views
- `templates/institutional-admin/` - Institutional admin views

Static assets include:
- **CSS:** Bootstrap 5 framework with custom styling across multiple stylesheets
- **JavaScript:** Vanilla JS with Bootstrap 5 components. Face-api.js for client-side face detection and descriptor computation. Custom modules for QR code scanning, SSE event streams, device fingerprinting, and dashboard interactivity.
- **WebFonts:** Custom icon fonts

The frontend communicates with the backend exclusively through the RESTful JSON API at `/api/`. Real-time updates use **Server-Sent Events (SSE)** via the `/api/institutional/events/stream` endpoint, which pushes attendance events, notifications, and dashboard updates as they occur.

### 3.3 Backend Architecture

The backend is a **monolithic Flask application** organized into services. The application factory pattern (`create_app()`) enables environment-specific configuration:

1. **Startup Sequence:**
   - Load configuration from environment/settings.py
   - Validate environment readiness and secret entropy
   - Initialize SQLAlchemy and create schemas
   - Initialize Firebase (mock or production)
   - Initialize authentication service
   - Initialize Zero-Trust Engine
   - Initialize dashboard data service
   - Initialize event service (SSE)
   - Initialize SMS and email services
   - Initialize payment and scheduling engines
   - Initialize attendance engine
   - Initialize offline queue service
   - Initialize MQTT service
   - Initialize biometric service
   - Initialize Innovation Engine (12 smart campus modules)

2. **Request Lifecycle:**
   - NGINX receives HTTPS request, terminates TLS, applies rate limiting
   - NGINX proxies to Flask (Gunicorn WSGI)
   - Flask middleware chain executes: CORS headers → security middleware → Cloudflare security → comprehensive security → security reinforcements
   - Route handler executes with `@require_auth → @require_role → @log_access` decorators
   - Business logic in application layer services
   - Database operations through Firebase Firestore or SQLAlchemy

   - Audit log entry created

### 3.4 Distributed Architecture

The system is designed for **multi-node, multi-campus deployment**:

- **Central Cloud Instance:** Deployed at `attendrix.app` behind Cloudflare CDN. Runs the full application stack: web server, database, MQTT broker, Redis, Celery workers.
- **Campus Nodes:** Each campus runs a local instance with its own MQTT broker and offline queue. Campus nodes synchronize with the central cloud when connectivity is available.
- **Node Types** (visible in the infrastructure dashboard):
  - Science Block
  - Engineering Block
  - HTTTC Annex
  - Central Library
  - Admin Block

Each node has a health status (healthy/degraded), success rate, and average sync duration. The system monitors P2P peer status and mesh health.

### 3.5 Communication Flow

**Attendance Marking Flow:**

1. Lecturer creates attendance session via `POST /api/attendance/create-session` → `AttendanceSecurityService.create_attendance_session()` generates a unique session code and stores it in Firestore `attendance_sessions`.
2. Lecturer displays QR code (encoding the session code) to the class.
3. Student scans QR code with their device camera.
4. Student's device captures a face image using webcam → face-api.js computes a 128-dimension face descriptor.
5. Student's device collects device fingerprint (user agent, screen resolution, timezone, etc.).
6. Client sends `POST /api/attendance/mark` with session code, face descriptor, device fingerprint, IP address, and location.
7. Server validates:
   - Session is active and not expired (server-side check, not client-side)
   - Session code matches server record exactly
   - Face descriptor matches an enrolled face (Euclidean distance <= 0.45)
   - Device fingerprint is checked for anomalies
   - Geolocation is within allowed radius (if enabled)
   - No rapid succession or multiple device anomalies
8. If all checks pass, attendance record is created in Firestore `attendance_records`.
9. MQTT message published to `attendrix/attendance/{session_id}`.
10. SSE event pushed to subscribed dashboard clients.
11. Real-time dashboard updates for the lecturer (showing student name, photo, marking time).

**Offline Sync Flow:**

1. Operation is created as a document in the Firestore `offline_queue` collection with status `pending`.
2. When connectivity is available, the sync engine processes pending operations in FIFO order.
3. Each operation is dispatched to the appropriate handler (e.g., `_handle_mark_attendance` for attendance operations).
4. On success, status changes to `synced`.
5. On failure, retry count increments. Exponential backoff (`2^retry * base_delay` with jitter) determines next retry time.
6. After `max_retries` (5), status changes to `failed`.
7. Failed operations can be manually retried via the admin dashboard.

### 3.6 Authentication Workflow

1. User navigates to login form.
2. User submits email and password.
3. Cloudflare Turnstile CAPTCHA is verified.
4. Rate limiter checks: IP-based (10 requests per 5 minutes) and email-based (5 requests per 5 minutes).
5. Backend looks up user by email in Firestore `users` collection.
6. Persistent account lockout check: if `failed_login_attempts >= threshold` (5) and account is within lockout window (15 min), return 429.
7. Bcrypt password verification against stored `password_hash`.
8. Failed attempts increment; successful attempts reset the counter.
9. Password expiry check: if password is older than `PASSWORD_MAX_AGE_DAYS` (90), prompt password reset.
10. On success: generate access JWT (1 hour expiry) and refresh JWT (30 days expiry).
11. Return tokens and user data to client.
12. Client stores token (typically in HTTP-only cookie or localStorage).
13. All subsequent API requests include `Authorization: Bearer <token>` header.
14. `require_auth` decorator validates the JWT on every protected endpoint.

## SECTION 4: NETWORKING AND DISTRIBUTED SYSTEMS DOCUMENTATION

### 4.1 LAN Synchronization

Each campus node operates on its own LAN segment. When a student marks attendance within a lecture hall, the entire request lifecycle occurs within the campus LAN: the student's device sends the request to the local NGINX instance, which proxies to the local Flask application, which writes to the local Firebase Firestore cache or the local offline queue. This ensures that attendance marking is not dependent on WAN connectivity to the central cloud.

The MQTT broker on each campus LAN enables real-time communication between campus-internal components. For example, when a lecturer creates a session, the MQTT message is published within the campus LAN, enabling local dashboard updates without WAN latency.

### 4.2 Distributed Nodes

The system monitors and manages up to 6+ distributed nodes simultaneously. Each node is characterized by:

- **Node name:** Human-readable identifier (e.g., "Science Block")
- **Status:** healthy, degraded, or offline
- **Success rate:** Percentage of successful sync operations
- **Average duration:** Mean sync time in milliseconds
- **Active sessions:** Number of concurrent attendance sessions

The infrastructure dashboard provides real-time visibility into node health, overloaded/underloaded nodes, and recommends load balancing actions.

### 4.3 Node-to-Node Communication

Node-to-node communication uses a combination of:

1. **Firestore Real-time Sync:** Firebase Firestore natively propagates data changes across all connected clients. When one node writes to Firestore, all other nodes with active listeners receive the update.
2. **MQTT Pub-Sub:** The MQTT broker relays attendance events to all subscribed nodes. Topics like `attendrix/attendance/{session_id}` ensure events reach all interested parties.
3. **Offline Queue with Batched Sync:** When continuous connectivity is unavailable, nodes queue operations and synchronize in batches when connectivity is restored.

### 4.4 Real-Time Messaging with MQTT

MQTT provides the real-time messaging backbone. Key implementation details:

- **Broker:** Eclipse Mosquitto 2.x (containerized in docker-compose)
- **Protocol:** MQTT v3.1.1 (paho-mqtt client)
- **QoS Levels:** QoS 1 is used for attendance events (at-least-once delivery)
- **Last Will Testament:** Each client publishes a "status: offline" message as its will, ensuring other nodes detect disconnection
- **Topic Structure:**
  - `attendrix/attendance/{session_id}` - Attendance marking events
  - `attendrix/session/{session_id}` - Session lifecycle events
  - `attendrix/network/{device_id}` - Network status updates
  - `attendrix/notifications/{user_id}` - User notifications
  - `attendrix/system/health` - System health check
  - `attendrix/system/status/{client_id}` - Client online/offline status

The `MqttService` supports a mock mode for development where messages are stored in memory and can be inspected via `/api/mqtt/status`.

### 4.5 Offline-First Architecture and Queue Synchronization

The `OfflineQueueService` is the heart of the offline-first architecture. It implements:

1. **Store-and-Forward Queuing:** Operations are stored as Firestore documents with full payload serialization (JSON). When connectivity is available, the queue processor dispatches operations in FIFO order.

2. **Exponential Backoff Retry:** Failed operations use exponential backoff: `base_delay * 2^(retry-1)` with jitter, capped at 60 seconds. This prevents thundering herd problems during network recovery.

3. **Conflict Resolution:** Three strategies are supported:
   - Last-Writer-Wins (LWW): The most recent operation overwrites
   - Discard Local: Server state is kept
   - Force Local: Local state overwrites server

4. **Queue Health Monitoring:** The `get_queue_stats()` method returns operational metrics: total pending, synced, failed, conflicts, retry counts, oldest pending operation, and health status (healthy if `failed < 10` and `conflicts == 0`).

5. **Bandwidth-Aware Sync:** The `estimate_sync_duration()` method calculates estimated sync time based on queue size and average operation processing time (~500ms per operation). Data size in KB is estimated for bandwidth planning.

6. **Per-Node Sync Status:** The `get_node_sync_status()` method provides per-node breakdown, enabling administrators to identify nodes with sync problems.

### 4.6 Fault Tolerance and Failover

The system implements multiple fault tolerance mechanisms:

- **Graceful Degradation:** If Firebase is unavailable, the system falls back to mock mode (development) or uses the offline queue (production).
- **Connection Retry:** The MQTT service implements auto-reconnection with backoff.
- **Redis Failover:** Redis session store falls back to in-memory storage if Redis is unavailable.
- **Celery Retry:** All Celery tasks have automatic retry with exponential backoff.
- **Database Fallback:** SQLite can be used when PostgreSQL is unavailable.

### 4.7 Bandwidth Optimization

- **Batched Operation Processing:** The offline queue processes operations in batches of 25 to reduce network round-trips.
- **Selective Synchronization:** Queue operations are processed by priority, with critical attendance operations taking precedence.
- **Compressed Payloads:** Operation payloads are JSON-serialized and stored compactly.
- **Efficient Real-Time Updates:** SSE is used instead of WebSocket or polling for real-time updates, as SSE is more bandwidth-efficient and works through standard HTTP proxies.
- **Static File Caching:** NGINX serves static files with 30-day cache headers.

### 4.8 Multi-Campus Communication Architecture

The multi-campus communication follows a hub-and-spoke topology:

```
                    [Central Cloud - attendrix.app]
                          |         |         |
                     Cloudflare   Firestore   MQTT Broker
                          |         |         |
              +-----------+---------+---------+-----------+
              |             |             |               |
         [Science Block] [Engineering] [HTTTC Annex] [Central Library]
         Campus Node      Campus Node   Campus Node    Campus Node
```

Each campus node runs:
- Local NGINX + Flask instance
- Local MQTT broker (Mosquitto)
- Local offline queue
- Firestore client (with local persistence)

Synchronization between campus nodes and the central cloud occurs through Firestore's native real-time sync and the offline queue service for batched sync.

## SECTION 5: CYBERSECURITY DOCUMENTATION

### 5.1 Security Architecture Overview

Attendrix implements a defense-in-depth security architecture across 7 layers:

| Layer | Mechanism | Location |
|-------|-----------|----------|
| 1. Network | Cloudflare WAF, IP blocklisting, rate limiting | NGINX + Cloudflare |
| 2. Transport | TLS 1.2/1.3, HSTS, security headers | NGINX |
| 3. Authentication | JWT, bcrypt, WebAuthn/FIDO2, TOTP | auth_service + webauthn_service |
| 4. Authorization | RBAC, permission checks, multi-tenant isolation | rbac.py + firebase_service |
| 5. Application | Input sanitization, CSRF, anti-replay, rate limiting | security modules |
| 6. Database | Firestore rules, query filtering, document access control | firestore.rules + firebase_service |
| 7. Monitoring | Security event monitoring, threat scoring, forensic audit | security_monitor + forensic_logging |

### 5.2 Authentication Security

**Password Security:**
- Bcrypt hashing with salt (`bcrypt.gensalt()`) for all passwords
- Password policy enforcement: minimum 8 characters, uppercase, lowercase, digit, special character
- Password history (last 5 passwords) prevents password reuse
- Password expiry after 90 days
- Account lockout after 5 failed attempts (15-minute lockout window)
- Rate limiting: 5 attempts per email per 5 minutes, 10 attempts per IP per 5 minutes

**JWT Security:**
- Access tokens expire in 1 hour
- Refresh tokens expire in 30 days
- Unique `jti` (JWT ID) for each token enables individual revocation
- Token blacklist via Redis (`redis_token_blacklist`)
- Minimum 64-character secret key enforced at startup
- Placeholder pattern detection prevents weak keys

**WebAuthn/FIDO2:**
- Passwordless authentication for admin accounts
- `require_admin_webauthn` decorator mandates at least one passkey for admin actions
- Hardware-bound cryptographic authentication (platform authenticator or security key)

**CAPTCHA:**
- Cloudflare Turnstile for bot prevention on login, registration, and signup forms
- Configurable fallback to Google reCAPTCHA

### 5.3 Authorization Security

**Role-Based Access Control (RBAC):**
- Five roles with granular permission sets
- Decorator-based enforcement at the route level
- Permission class defines 30+ specific permissions

**Multi-Tenant Isolation:**
- Every database query automatically injects `institution_id` filter based on authenticated user
- Cross-institution reads are blocked and logged as security events
- Cross-institution writes raise `PermissionError`
- Per-user collections enforce ownership verification
- Super admin role bypasses institution scoping

**Firestore Security Rules:**
- Every collection has explicit `allow read/write` rules
- Functions enforce role checks: `isSuperAdmin()`, `institutionAdmin()`, `lecturer()`, `student()`
- Institution matching: `sameInstitutionRead()`, `sameInstitutionWrite()`
- Ownership verification: `isOwnDocument()`, `isOwnRequest()`
- Default deny for all unmatched paths (`allow read, write: if false`)

### 5.4 API Security

**Rate Limiting:**
- NGINX-level: separate zones for login (5r/m), register (3r/m), API (30r/m), admin (20r/m), attendance (10r/m), with connection limiting
- Application-level: IP-based and email-based rate limiting with block duration
- Redis-backed persistent rate limiting when available

**Input Validation:**
- InputSanitizer module sanitizes emails, strings, and JSON bodies
- Server-side field validation for all form submissions
- Honeypot fields detect bot submissions
- Disposable email domain blocklist
- HTML escaping for stored data

**CSRF Protection:**
- 64-byte CSRF tokens validated server-side
- Token expiry configurable (default 1 hour)
- Honeypot timestamp validation prevents automated submissions

**API Hardening:**
- Request signature validation (anti-replay protection)
- Schema validation for all API request bodies
- JWT rotation management
- Attack throttling for brute-force prevention
- Security middleware chain for composable protection

### 5.5 Session Security

- `SESSION_COOKIE_HTTPONLY = True`: Prevents JavaScript access to session cookies
- `SESSION_COOKIE_SECURE = True`: Cookies only sent over HTTPS
- `SESSION_COOKIE_SAMESITE = 'Lax'`: Protects against CSRF
- Redis-backed session store for persistent sessions
- Session timeout: 1 hour (configurable)

### 5.6 Security Monitoring and Incident Response

**Security Monitor** (`security_monitor.py`):
- Centralized security event collection and analysis
- Event types tracked: `system_startup`, `login_success`, `login_failed`, `logout`, `403_forbidden`, `404_not_found`, `rate_limited`, `500_error`, and custom events
- Severity classification: info, warning, critical
- Risk scoring for each event

**Threat Scoring** (`ThreatScorer`):
- Aggregates risk scores to identify active threats
- IP-based threat tracking
- Authentication anomaly detection

**Forensic Audit Logging** (`ForensicAuditLogger`):
- Immutable audit trail for all security events
- User-specific trail queries
- Event-type filtering
- Retention period: 365 days (configurable)

**Security Dashboard API:**
- `/api/security/dashboard` - Summary, threats, blocked IPs, recent alerts, authentication summary, top threat IPs, security score
- `/api/security/events` - Filtered event queries
- `/api/security/blocked-ips` - Currently blocked IP addresses
- `/api/security/audit-log` - Detailed audit trail with user/event-type filtering
- `/api/security/threats` - Active threat identification

### 5.7 Device Fingerprinting

- SHA-256 hash of user agent, IP, screen resolution, timezone, language, and additional browser properties
- Trust scoring with adaptive threshold (increases with successful verifications)
- New device detection triggers suspicious activity flags
- Multiple new devices in 7-day window increases risk score

### 5.8 Anti-Proxy Attendance Security

The anti-proxy system (`AttendanceEngine`) is specifically designed to prevent proxy attendance. It detects:

1. **Multiple Devices:** Same student marking from different IPs/user agents in the same session
2. **Impossible Location:** Geolocation distance exceeds the allowed radius from the lecture hall
3. **Rapid Succession:** More than 2 attendance marks within 5 minutes for the same student
4. **Unusual IP Pattern:** Student marking from an IP completely different from their historical pattern
5. **Device Mismatch:** New device fingerprint with no prior history
6. **Time Anomaly:** Student marking at a time significantly different from their historical pattern (30+ minutes deviation)

Suspicious activities are logged with risk scores. Activities exceeding risk score 50 are flagged for administrator review.

### 5.9 Security Risks Prevented

| Risk | Prevention |
|------|------------|
| Proxy attendance | Face verification + device fingerprint + geolocation + IP validation |
| Account takeover | Rate limiting + lockout + MFA + password history |
| Data breach | Multi-tenant isolation + Firestore rules + encryption + access auditing |
| Brute force | Progressive delay + account lockout + CAPTCHA + rate limiting |
| Session hijacking | HTTP-only cookies + Secure flag + SameSite + JWT short expiry |
| CSRF | Token validation + SameSite cookies + referer checking |
| XSS | Input sanitization + HTML escaping + CSP headers |
| MITM | TLS 1.2/1.3 + HSTS + certificate pinning |
| Bot attacks | Cloudflare WAF + Turnstile + honeypot + rate limiting |

| Enumeration | Generic error messages ("Invalid email or password") |
| Data scraping | Rate limiting + per-endpoint throttling |

## SECTION 6: DATABASE DOCUMENTATION

### 6.1 Database Architecture

Attendrix uses a **hybrid database architecture**:

1. **Primary Database: Firebase Firestore (NoSQL)**
   - All operational data lives in Firestore: users, institutions, courses, attendance sessions, attendance records, biometric enrollments, device fingerprints, notifications, vouchers, leave requests, activity logs, security logs, system configurations, and demo bookings.
   - Collections are organized with document IDs as primary keys.
   - Multi-tenant isolation is enforced at both the application layer (firebase_service.py) and database layer (firestore.rules).

2. **Secondary Database: PostgreSQL via SQLAlchemy (Relational)**
   - Used for complex queries, analytics, and reporting.
   - SQLAlchemy models are defined in `demo_sql_repositories.py` and `feedback_models.py`.
   - Schema migrations are managed through Alembic.
   - The database connection is optional; SQLite is the development default.

3. **Cache Layer: Redis**
   - Celery broker and result backend
   - Session store (when REDIS_SESSION_ENABLED is true)
   - Rate limiting storage
   - Token blacklist

4. **Offline Storage: JSON File (Mock Database)**
   - `mock_database.json` serves as the development/test database.
   - All CRUD operations in mock mode read/write this JSON file.
   - Persists between server restarts.

5. **Attendrix Mail Database: SQLite**
   - `MailQueue`, `MailTemplate`, `MailAuditLog`, `MailSmtpProfile` tables for the queue-based internal email subsystem.

### 6.2 Firestore Collections

**Communication Collections:**

### 6.3 Data Relationships

Although Firestore is a NoSQL database, relationships are maintained through reference fields:

- `users.institution_id` → `institutions.id`
- `courses.institution_id` → `institutions.id`, `courses.department_id` → `departments.id`
- `attendance_sessions.course_id` → `courses.id`, `attendance_sessions.lecturer_id` → `users.id`
- `attendance_records.session_id` → `attendance_sessions.id`, `attendance_records.student_id` → `users.id`
- `biometric_enrollments.user_id` → `users.id`, `biometric_enrollments.institution_id` → `institutions.id`

### 6.4 Data Synchronization Across Nodes

When a document is created or updated in Firestore, Firebase's real-time synchronization engine automatically propagates the change to all connected clients. For operations created during offline periods, the offline queue service manages batched synchronization.

The synchronization flow for offline-created data:
1. Operation is stored as a document in `offline_queue` collection with payload, status, and metadata.
2. Sync processor reads pending operations in FIFO order.
3. For each operation, the handler function is called with the deserialized payload.
4. Handler creates/updates the target document (e.g., `attendance_records`).
5. On success, queue document status changes to `synced`.
6. Old synced entries are periodically cleaned up (default: older than 24 hours).

### 6.5 Indexing and Performance

Firestore automatically indexes all single-field queries. Composite indexes would be created as needed for complex queries. The database_schema.py defines indexes for frequently queried fields:

- `users`: email (unique), institution_id, role
- `attendance_sessions`: course_id, lecturer_id, session_code
- `attendance_records`: session_id, student_id, mark_time
- `security_logs`: user_id, institution_id, event_type, created_at

The in-memory rate limiter and Redis caching layer reduce database load for high-frequency operations like login attempts and session validation.

### 7.3 Attendance Registration Module

**Location:** `src/application/offline_queue_service.py`

**What it does:** Manages offline data synchronization with exponential backoff and conflict resolution.

**How it works:**

3. Each operation is dispatched to its handler function via `handler_map`.
4. Success → status = `synced`. Failure → retry with exponential backoff.
5. After `max_retries` (5) → status = `failed`.
6. Failed operations can be retried via `retry_failed()`.
7. Old synced entries cleaned up via `clear_synced()`.
8. Queue health monitored via `get_queue_stats()`.

**Conflict resolution strategies:** Last-writer-wins (default), discard local, force local, manual resolution.

**Networking involvement:** The synchronous engine is the core networking resilience component. It handles network partitions by storing operations locally until connectivity is restored.

## SECTION 10: FINAL DEFENSE PREPARATION

### 10.1 Likely Supervisor Questions and Answers

**Q1: Why did you choose Flask over Django?**

**A:** Flask was chosen for its lightweight, modular architecture that aligns with Clean Architecture principles. Attendrix separates presentation, application, domain, and infrastructure layers. Flask's explicit routing and extension-based design allows us to compose exactly the services we need (SQLAlchemy, MQTT, Firebase, Celery) without Django's heavy ORM and admin overhead. Flask's blueprints map directly to our modular domain boundaries.

**Q2: Explain the multi-tenant isolation architecture.**

**A:** Multi-tenant isolation is enforced at three layers:
1. Application layer: `FirebaseService._enforce_query_filters()` automatically injects `institution_id` into all Firestore queries based on the authenticated user's token. Cross-institution reads are blocked and logged as security events.
2. Decorator layer: `require_role` and `require_institution_access` decorators verify role and institution before any route handler executes.
3. Database layer: Firestore security rules (`firestore.rules`) enforce the same isolation at the database level using functions like `sameInstitutionRead()` and `sameInstitutionWrite()`. Even if an attacker bypasses the application layer, the database itself blocks unauthorized cross-tenant access.

**Q3: How does the system handle offline attendance marking?**

**A:** The `OfflineQueueService` implements a store-and-forward architecture. When the network is unavailable, all write operations (attendance marking, session creation, user updates) are serialized as JSON documents in the Firestore `offline_queue` collection. When connectivity is restored, the sync engine processes pending operations in FIFO order, dispatching each to its handler function. Exponential backoff with jitter (base 2s, capped at 60s) prevents thundering herd on reconnection. After 5 retries, operations are marked as failed and can be manually retried via the admin dashboard.

**Q4: How does face verification prevent proxy attendance?**

**A:** Face verification uses face-api.js to compute a 128-dimension face descriptor on the client side. This descriptor is a mathematical representation of facial features—raw images are never stored. During enrollment, the descriptor is stored in Firestore's `biometric_enrollments` collection. During attendance, the live descriptor is compared against all enrolled descriptors using Euclidean distance. A threshold of 0.45 (configurable) determines a match. This prevents proxy attendance because the physical student must be present to have their face scanned. The system further supports `verify_face_against_all()` which matches against all enrolled students in the institution, preventing a student from using another student's credentials.

**Q5: What happens if the internet goes down during an attendance session?**

**A:** The system has three layers of resilience:
1. The `OfflineQueueService` queues the attendance marking operation locally. The queue document in Firestore stores the full payload with status `pending`.
2. When connectivity returns, the sync engine processes the queue, dispatching operations to the appropriate handlers.
3. The MQTT broker continues operating on the campus LAN, so real-time updates within the campus still work even without internet.

### 10.2 Networking-Related Questions

**Q6: Explain the distributed node architecture.**

**A:** Attendrix supports a hub-and-spoke topology. The central cloud instance at attendrix.app is the system of record, running the full stack: web server, Firebase, MQTT broker, Redis, and Celery workers. Campus nodes (Science Block, Engineering Block, HTTTC Annex, Central Library, Admin Block) each run local instances that synchronize with the central cloud. The system monitors node health, success rates, sync durations, and provides load balancing recommendations.

**Q7: How does MQTT enable real-time communication?**

**A:** MQTT uses a publish-subscribe model with hierarchical topics. When a student marks attendance, `MqttService.publish()` sends a message to `attendrix/attendance/{session_id}` with QoS 1 (at-least-once delivery). Any component subscribed to that topic (dashboards, analytics engines, other campus nodes) receives the message immediately. The Mosquitto broker on each campus LAN handles local routing, while the central broker handles inter-campus routing.

**Q8: How did you handle network partitions in a multi-campus setup?**

**A:** Network partitions are handled through the offline queue service. Each campus node operates independently during a partition, queuing operations locally. When the partition heals, the sync engine processes all queued operations in order. Exponential backoff prevents immediate retry floods. Conflict resolution uses last-writer-wins by default, with support for manual resolution of specific conflicts.

**Q9: How does the system optimize bandwidth for synchronization?**

**A:** Bandwidth optimization strategies include: batched processing (25 operations per batch), selective synchronization by priority, compressed JSON payloads, SSE instead of WebSocket for real-time updates, and static file caching with 30-day cache headers at the NGINX level.

### 10.3 Cybersecurity-Related Questions

**Q10: How is data protected at rest and in transit?**

**A:** In transit: All traffic uses TLS 1.2/1.3 with strong cipher suites (ECDHE-ECDSA-AES128-GCM-SHA256 etc.). HSTS enforces HTTPS at the browser level. At rest: Passwords are hashed with bcrypt. Firebase Firestore encrypts all data at rest by default. API responses exclude sensitive fields (password_hash is stripped before returning user data).

**Q11: How does the system prevent SQL injection or NoSQL injection?**

**A:** The system uses parameterized queries through SQLAlchemy ORM and Firebase Firestore's built-in query API. InputSanitizer validates and sanitizes all user input before it reaches database operations. Firestore security rules provide a second layer of defense. The `api_security.py` module includes schema validation for all API requests.

**Q12: Explain how the anti-proxy attendance mechanisms work together.**

**A:** The `AttendanceEngine._perform_security_checks()` runs six concurrent checks:
1. IP restriction (if enabled on the session)
2. Geolocation distance calculation (geopy.geodesic()) against allowed location
3. Device fingerprint matching (SHA-256 hash of UA, IP, screen, timezone, etc.)
4. Rapid succession detection (more than 2 marks in 5 minutes)
5. Multiple device detection (same session, different IPs/user agents)
6. Time anomaly detection (deviation from historical marking pattern > 30 min)
Each check contributes to a risk score. Activities exceeding 50 are flagged as suspicious and logged for administrator review.

### 10.4 Distributed Systems Questions

**Q13: How does the offline queue handle concurrent updates from multiple nodes?**

**A:** The offline queue uses Firestore as the coordination layer. Each queue entry has a checksum field computed from the payload. Conflict resolution supports four strategies: last-writer-wins (based on timestamp), discard local (keep server state), force local (overwrite server state), and manual resolution (admin provides merged data). The sync engine processes entries sequentially within each institution to minimize conflicts.

**Q14: How do you ensure eventual consistency across campus nodes?**

**A:** Eventual consistency is achieved through: Firestore's native real-time synchronization (changes propagate to all connected clients within seconds), the offline queue service (batched sync for operations created during offline periods), and periodic full-sync triggers. The sync engine's `get_node_sync_status()` provides per-node visibility into consistency status.

### 10.5 Architecture Questions

**Q15: Justify the use of Firebase Firestore over a traditional relational database.**

**A:** Firestore was chosen as the primary database for three reasons:
1. Real-time synchronization is built-in—we get cross-campus data propagation without writing custom sync code.
2. Security rules provide server-enforced access control at the database level.
3. Serverless scaling eliminates database server management. PostgreSQL is retained as a secondary option for complex reporting queries that benefit from JOIN operations and aggregations.

### 10.6 Implementation Questions

**Q16: How was the face verification system tested?**

**A:** Face verification testing involved: verifying Euclidean distance computation against known face descriptor pairs, testing threshold sensitivity (0.45 as the optimal balance), testing false positive rate with random descriptors, testing enrollment/verification/revocation lifecycle, and verifying cross-institution isolation (a student from one institution cannot match against faces from another).

**Q17: What is the significance of the 128-dimension face descriptor?**

**A:** The 128-dimension descriptor is the standard output of face recognition neural networks (FaceNet-style models). It represents facial features in a high-dimensional space where Euclidean distance correlates with facial similarity. 128 dimensions provides sufficient discriminative power for a university-scale deployment while keeping storage and computation efficient. The entire system handles thousands of students without performance degradation.
